# Roofline: where each workload sits against the RTX 5070's speed of light

[gpu-systems-lab](../README.md) / `docs/` · [← Results](RESULTS.md) · [Code guide](CODE-GUIDE.md)

A roofline plot puts every workload at its **arithmetic intensity** (FLOPs per byte of DRAM
traffic) and the FLOP rate it actually reached. The ceiling is `min(compute peak, intensity ×
memory bandwidth)`. To the left of the ridge point a kernel can at best stream data at memory
speed (memory-bound); to the right it can at best keep the ALUs or tensor cores busy
(compute-bound). The gap between a dot and the roof above it is what's left to win.

Numbers are generated by [tools/roofline.py](../tools/roofline.py) (unit-tested in
[tools/test_roofline.py](../tools/test_roofline.py)) from measurements already in this repo. The
results site draws them as an interactive chart.

## The roofs (measured, not datasheet)

| Ceiling | Value | Where it was measured |
|---|---:|---|
| DRAM bandwidth | **634 GB/s** | `cub::DeviceReduce::Sum`, the fastest read stream ([cuda/README.md](../cuda/README.md)) |
| DRAM, datasheet | 672 GB/s | GDDR7 spec; dashed line, reference only |
| FP32 | **23.7 TFLOPS** | cuBLAS FP32 GEMM 8192² ([RESULTS.md](RESULTS.md#single-gpu)) |
| BF16 (tensor cores) | **67.7 TFLOPS** | cuBLAS BF16 GEMM 8192² (same table) |

These are measured ceilings, an "empirical roofline" as tools like the Empirical Roofline Toolkit
produce: the best this card has shown it can do, so 100% is reachable. Ridge points: 23.7e12 /
634e9 = **37 FLOP/byte** (FP32) and **107 FLOP/byte** (BF16).

## How each point is computed

| Workload | FLOPs | Bytes (compulsory DRAM traffic) |
|---|---|---|
| `vector_add` | 1 per element | 12 per element (read a, b, write c) |
| warp-shuffle reduction | 1 per element | 4 per element |
| fused bias + GELU(tanh) | ~10 per element (add, cube, 2 FMAs, tanh, scale) | 8 per element (fp32 in, fp32 out) |
| RMSNorm (bf16) | 4 per element (square, accumulate, two multiplies) | 4 per element (bf16 in, bf16 out) |
| square GEMM, N = 4096 | 2N³ | 3N² × 4 (A and B read once, C written once) → N/6 = 683 FLOP/B |
| GPT train step (JAX) | 6 × params × tokens, the standard model-FLOPs count | not modelled: dense GEMMs dominate, so it's plotted against the compute roof only |
| vLLM decode, Qwen2.5-1.5B | 2 × 1.54B params × requests in the batch, per step | **weights only:** 3.08 GB of bf16 weights read once per step |

The decode points are estimates. The model counts only weight traffic and decode FLOPs. KV-cache
reads add bytes, and the 512-token prefills add FLOPs. Steps per second = output tokens/s ÷
concurrent requests, from the vLLM table in RESULTS.md.

## What the plot says

1. **The streaming kernels sit on the memory roof.** The reduction reaches 99% of it, `vector_add`
   93%, and the Triton bias+GELU and RMSNorm custom op 88–89%. The hand-written CUDA bias+GELU is
   at 77%: the 4-byte-load version this repo improved on. Beyond these figures, the only way
   forward is moving fewer bytes, as fusion does.
2. **Every elementwise or normalization kernel is memory-bound by a factor of 30 or more.** At 1
   FLOP/byte they could use at most 634 GFLOPS of a 23.7 TFLOPS card, under 3% of its compute.
   That's why fusion and precision (bf16 halves the bytes) matter more than math tricks for them.
3. **GEMM is the only thing here that can be compute-bound.** cuBLAS reaches 89% of the FP32
   roof. The naive kernel sits at the same intensity in theory but reaches 8%: it doesn't actually
   achieve the compulsory traffic, because without tiling every element of A and B is re-read
   from L2/DRAM thousands of times. Its true intensity is far lower than 683. The CUDA kernels'
   1.96 TFLOPS was measured in [cuda/README.md](../cuda/README.md).
4. **Training is compute-bound.** The JAX GPT step reaches 72% of the BF16 tensor-core roof.
5. **LLM decode moves right as batching grows, and falls away from the roof.** With one request,
   decode is ~1 FLOP/byte and runs at an estimated 530 GB/s, 84% of the memory roof: one user is a
   bandwidth problem. At 64 requests each weight read serves 64 tokens (64 FLOP/byte, 13.6
   TFLOPS), but that's only 34% of what the roof allows at that intensity. The weights-only model
   is missing what limits it there: KV-cache reads grow with batch × context, plus attention,
   sampling and scheduler overhead. That's consistent with the KV cache filling up at 256
   concurrent requests in the serving table.
