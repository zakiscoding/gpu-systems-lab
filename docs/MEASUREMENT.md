# Measurement method: warm-up, repeats, confidence intervals, GPU clocks

[gpu-systems-lab](../README.md) / `docs/MEASUREMENT.md` · [Results](RESULTS.md) · [cuda/](../cuda/README.md) · [tools/benchstat.py](../tools/benchstat.py)

The earlier write-ups here mostly report **one run** of each benchmark: the mean of N timed
iterations inside a single process. That number hides three things:

1. **Run-to-run variance.** A new process gets new allocations, a new clock ramp and different L2 state.
2. **First-run cost.** The first launch pays for module loading, JIT and a cold clock.
3. **Clocks.** The RTX 5070 boosts between about 2.5 and 2.9 GHz depending on load, power and
   temperature. Two numbers taken at different clocks are not comparable.

So a claim like "the warp-shuffle reduction ties CUB" can't be checked from a single run. This page
sets the method and applies it to the hand-written CUDA kernels in [cuda/](../cuda/README.md).

## Method

[tools/benchstat.py](../tools/benchstat.py) wraps any benchmark that prints rows of
`name  ms  metric  max_err  ok`, which is what every `cuda/` program prints:

```bash
python3 tools/benchstat.py run --warmup 2 --repeats 10 --out results/rigor/fused.json -- cuda/build/fused
python3 tools/benchstat.py table "results/rigor/*.json"
```

- **Warm-up:** 2 full runs of the program, output thrown away. Each program also does its own
  in-process warm-up before timing, as before.
- **Repeats:** 10 separate processes. Each one reports the mean of its own timed iterations.
- **Statistics per row:** n, mean, standard deviation, coefficient of variation (CV), min and max,
  plus a **95% confidence interval for the mean**: mean ± t(0.975, n−1) · sd / √n, using Student's t
  because n is small (t = 2.262 for n = 10).
- **GPU state:** `nvidia-smi` is read before and after every repeat (SM clock, memory clock,
  temperature, power, utilization) and saved with the result. The clocks are **recorded, not
  locked.** Locking them (`nvidia-smi -lgc`) needs admin rights on the Windows host, and under WSL the
  driver belongs to Windows. Recording them at least shows when two results ran at different clocks.
- **Correctness:** every repeat must exit 0, and every program checks its own output (it prints PASS).
  `all_rc_zero` in the JSON records this.

**When are two results different?** If their 95% intervals don't overlap, the difference is real
for this setup. If they overlap, treat the two as equal unless more repeats separate them.

[tools/test_benchstat.py](../tools/test_benchstat.py) checks the statistics against hand
computation, the t table, the single-sample case and the row parser (4 tests).

## What changed in the conclusions

1. **Run-to-run noise is tiny on this card: every CV is ≤ 0.5%.** The ±CI half-widths are 0.0–0.4%
   of the mean. So differences of a few percent between kernels are real, and the single-run numbers
   in the older tables were already close to the mean of their own setup.
2. **"The warp-shuffle reduction ties CUB" doesn't hold up.** With intervals, warp shuffle is
   624.7 ± 0.8 GB/s and CUB is 613.5 ± 2.1. The intervals don't overlap, so the hand-written kernel
   is **1.8% faster** here. The original single run had CUB ahead (634 vs 630). That was within
   noise of one run, but the order flipped, which a single run can't reveal.
3. **The fusion speedup is 1.98x**, not 1.93x: 2.072 ms unfused vs 1.044 ms fused, both with
   CIs under 0.2%. That's essentially the 2x cut in DRAM traffic.
4. **Today's numbers differ from the originals by 1–8%, mostly because the setup changed, not
   because of noise.** The original `cuda/` table came from a native Ubuntu 24.04 boot with driver
   595.99. Today's ran under WSL with the Windows driver, next to `vllm-chat`'s reserved memory, and
   at recorded clocks. For example, cuBLAS FP32 moved from 21,017 to 22,736 GFLOPS (+8%) and
   vector_add from 569 to 563 GB/s (−1%). The noise within each setup (≤ 0.5%) is much smaller than
   these shifts, so **compare numbers only within one setup**. That's why each table now names its
   setup.
5. **The clock differs between programs, not between repeats.** Reduction ran at a steady 2880 MHz,
   matmul at 2850–2857, while vector_add and fused moved between 2535 and 2767. Memory-bound
   kernels at a lower SM clock lose nothing, because DRAM sets their speed. The memory clock was
   13,801 MHz in every repeat.
